# AI Assistant Workflow for Commits & Pushes

## 🚨 CRITICAL: Pull Request Workflow (MANDATORY)

**NEVER push directly to `dev` or `main` branches!** All changes must go through Pull Requests.

## When User Asks to Commit and Push

### Step 1: Check Current State
```bash
git status
git branch  # Check current branch
```

### Step 2: Ensure You're on a Feature Branch (NOT dev/main)
```bash
CURRENT_BRANCH=$(git branch --show-current)

# If on dev or main, create a feature branch
if [ "$CURRENT_BRANCH" = "dev" ] || [ "$CURRENT_BRANCH" = "main" ]; then
    echo "⚠️ WARNING: You're on $CURRENT_BRANCH branch!"
    echo "Creating feature branch instead..."
    # Ask user for feature name or use descriptive default
    git checkout -b feature/$(date +%Y%m%d)-changes
    CURRENT_BRANCH=$(git branch --show-current)
fi
```

### Step 3: Pull Latest Changes from dev (CRITICAL)
```bash
# Always sync with dev before committing
git fetch origin
git checkout dev
git pull origin dev

# Return to feature branch and update it
git checkout $CURRENT_BRANCH
git merge dev  # or git rebase dev if preferred
# If conflicts occur, resolve them before proceeding
```

### Step 4: Stage Changes
```bash
git add .
# Or selectively: git add <specific-files>
```

### Step 5: Commit with Descriptive Message
```bash
# Use clear, descriptive commit messages following conventional commits
git commit -m "type: brief description of changes"
# Examples:
# - "feat: add user authentication endpoint"
# - "fix: resolve login form validation issue"
# - "refactor: update API response format"
# - "docs: update collaboration workflow"
```

### Step 6: Push to Feature Branch (NOT dev!)
```bash
# Push to the feature branch you're on
git push origin $CURRENT_BRANCH

# If first push, set upstream:
git push -u origin $CURRENT_BRANCH
```

### Step 7: Create Pull Request (REQUIRED)
```bash
# Inform user they need to create PR on GitHub
echo "✅ Changes pushed to $CURRENT_BRANCH"
echo "📝 Next step: Create Pull Request on GitHub:"
echo "   https://github.com/OnarYusifov/scrims/compare/dev...$CURRENT_BRANCH"
echo ""
echo "⚠️ DO NOT merge directly to dev! Wait for review and approval."
```

## Important Rules

1. **NEVER push directly to `dev` or `main`** - Always use feature branches
2. **ALWAYS create Pull Request** - All changes must be reviewed
3. **NEVER merge your own PR** - Wait for review and approval
4. **ALWAYS pull from dev first** - Sync before committing
5. **If conflicts occur** - Resolve them before pushing
6. **If on wrong branch** - Create feature branch immediately
7. **If uncommitted changes exist** - Handle them (commit, stash, or discard)

## Quick Workflow Script

When user says "commit and push", execute:
```bash

git status
CURRENT_BRANCH=$(git branch --show-current)

# 4. Return to feature branch and sync
```

## Conflict Handling

If merge conflicts occur:
1. Show user which files have conflicts: `git status`
2. Let user know conflicts need manual resolution
3. After resolution: `git add . && git commit -m "Resolve merge conflicts"`

## Branch Management

- **If user is on `dev` or `main`**: IMMEDIATELY create feature branch - never commit to these!
- **If no branch exists**: Create one with `git checkout -b feature/description`
- **After push**: ALWAYS remind user to create Pull Request on GitHub
- **Never suggest merging directly**: Always go through PR process

## Pull Request Workflow (For AI Assistants)

When helping with PRs:

1. **Check if PR exists**: Look for open PRs from the feature branch
2. **Review changes**: Help user understand what changed
3. **Resolve conflicts**: If PR has conflicts, help merge dev into feature branch
4. **Wait for approval**: Never merge PR without explicit user approval
5. **After merge**: Clean up local branch with `git branch -d feature/branch-name`

## Communication with Other AI Assistants

When working with collaborators who also use AI:

1. **Use clear commit messages**: Follow conventional commits format
2. **Document changes in PR description**: Explain what and why
3. **Tag related issues/PRs**: Reference related work
4. **Be explicit about breaking changes**: Mark with `BREAKING:` prefix
5. **Keep PRs focused**: One feature/fix per PR
6. **Update documentation**: If workflow changes, update this file and COLLABORATION.md
